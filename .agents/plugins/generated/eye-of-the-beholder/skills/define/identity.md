# Optional identity handbook

Use the sections needed for the current identity decision. Define and explore govern routing and collaboration. These prompts help identify a visual system; they do not prescribe an interview programme, mandatory artifacts or universal aesthetic rules.

## Purpose and positioning

Start with existing product evidence and the conversation. Identify who uses the product, the outcome it serves and what should distinguish the experience. Missing purpose information can justify one focused question. A screen request does not require stakeholder interviews. Research competitors or adjacent references when that resolves a concrete uncertainty, with attribution and a clear role for each reference.

Personality words are hypotheses. Pair them with actual images and contrasting examples, then use explore to determine what the user means. A useful anti-attribute names a failure to avoid in this product; it is not a ban on an entire visual technique.

## Visual foundations

Consider the following as a connected system, using accepted reference images:

- Typography: reading tasks, hierarchy, density, language coverage and the relationship between display and body text. Verify fonts in the actual renderer before making a fidelity claim.
- Color: palette relationships, accessibility, state meanings and material response to light. A familiar numeric palette formula does not determine whether the composition works.
- Form: silhouette, proportions, curvature, edges, depth and lighting. Different shadow treatments can be coherent when their roles and lighting are intentional.
- Motion: continuity, focus, feedback, rhythm and the user's control. Verify transitions in the runtime; stills only propose their key states.
- Imagery: medium, viewpoint, lighting, texture and compositional rules. Reference-guided generation can explore families of assets, but inspect every result for drift.

Tie reusable decisions to accepted images and observed product needs. Do not infer a prescribed radius, font family or shadow style from an adjective such as friendly or professional.

## From identity to reusable implementation

Record semantic channels before adding new encodings. Separate foundation values (palette, spacing, motion), semantic roles (surface, text, focus, warning) and component decisions where this separation helps reuse. The scale should fit the product: a handful of shared constants can be sufficient for a small app.

For a component, document the purpose, supported states and combinations, relevant scales, interaction, accessibility, defining visual qualities and a current rendered example. Include do/don't examples only when they explain a real distinction.

Use the templates as optional starting points: visual-language for accepted image anchors and decisions; brand for a broader identity request; design-system for tokens, component contracts and governance. Extend existing canonical records rather than creating parallel sources of truth.

## Maintenance

Agree who can change identity decisions and how changes become accepted. Distinguish experiments from accepted standards and rejected directions. Preserve scoped rejection reasons so the same failed treatment does not return under a new name. Governance and versioning must follow the actual project's rules; sample template policies do not override them.
