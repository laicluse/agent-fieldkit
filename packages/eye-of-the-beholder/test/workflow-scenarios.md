# Manual workflow behavior probes

Read the public skills and answer each scenario with the route, next action, whether image generation is required, and what must wait. Evaluate against the expected boundary, not exact wording. Assume a working reference-capable image generator and render capture route except where a scenario explicitly removes one. These probes cannot establish aesthetic quality or prove that a generation backend is available.

| Scenario | Expected behavior |
| --- | --- |
| Add a new focus treatment; a visual-language document already exists. | Explore with actual image references and image generation; existing prose does not settle the new form; await visual acceptance before dependent implementation. |
| Change an accepted component's padding by exactly 8 px. | Review/direct correction and real render; no mandatory interview or concept generation. |
| The last two visual corrections still look ugly. | Reopen the failed assumption or references through explore; do not select the least bad candidate or add another decorative variation. |
| The material is accepted but the highlight mechanism is rejected. | Preserve only the accepted material; explore the unresolved mechanism; do not implement the rejected combination. |
| None of the candidates is acceptable. | Record scoped rejection, revisit the premise, offer a new consequential decision; no forced winner. |
| Image generation is unavailable. | Disclose and agree a fallback before substituting CSS/SVG or text proposals. |
| Could image generation help our workflow? | Discuss the method; do not generate or change the product merely because the tool was mentioned. |
| Workflow focus and user selection must be distinguishable together. | Establish a coherent state family in product context, then verify simultaneous states, zoom and motion in the runtime after visual acceptance. |
| First complaint: this existing header looks cramped. | Review the actual render and diagnose the spacing axis before proposing a new treatment. |
| An annotated screenshot requests a new treatment. | Classify product pixels and commentary, then explore; the readback does not bypass the visual decision. |
| Build this greenfield settings screen using our accepted components. | Reuse and review; do not require a brand interview. |
| Add the feature; later the proposed concept is accepted. | Continue the already-authorized implementation without another go, if scope is unchanged. |
| A generation tool exists but accepts no reference images. | Identify that limitation and agree a suitable route; do not claim reference conditioning occurred. |
| A directly invoked review discovers unresolved new form. | Route to explore using the same image and decision rules as the main entry. |
| The image is generated but the user sees only a filesystem path. | Resolve a visible sharing route before asking for a design decision. |
| All named matching axes pass but aggregate confidence is below 95. | Report the scoped match with its evidence and explain the unrelated aggregate differences; do not claim full-image equivalence. |
| Directly invoked define is asked for one component in an accepted identity. | Preserve identity and route the component decision to explore or review as appropriate. |
| Explore ideas only; no implementation requested. | Stop at the concept decision and record it; do not implement. |
| No runtime capture route works. | Disclose the limitation and continue useful diagnosis or setup; no visual-verification claim. |
| The user types the retired taste-test name. | If the message is visible to the agent, explain the rename and route to explore; do not pretend the retired command still exists. |
| Match this new button to the existing header button's padding and radius. | Use the distinct header reference and named-axis table with rendered reference/result evidence; preserve other accepted behavior. |
